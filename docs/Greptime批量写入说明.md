# Greptime批量写入说明

## 写入链路

处理服务使用官方 Java Ingester 0.16.0 的 gRPC Bulk（Arrow）写入遥测参数、正常整帧和异常整帧。官方项目采用 Apache 2.0 许可证，项目地址为 https://github.com/GreptimeTeam/greptimedb-ingester-java 。

流程为：解析与校准完成 → 原有有界异步入库线程池组装存储记录 → 提交有总额度的合并缓冲 → 同任务同对象跨帧汇总 → 时间、行数或字节条件触发 → 独立合并入库线程首次建表和目录登记 → 按对象分表发送参数批次 → 检查服务端确认行数 → 批量发送并确认整帧。

采集及解析线程不等待数据库网络响应。MQ、实时缓存与WebSocket继续使用各自的处理链路，前端接口的参数、字段和返回结构没有变化，不需要重新导入Apifox接口。

管理服务不引入写入SDK。查询、初始化数据库、按对象创建分表、目录登记及过期删除继续执行现有MyBatis XML。普通帧不获取查询连接池；只有首次对象建表或首次任务与接口登记才需要查询连接。

## 批次与并发

默认同一任务、同一对象的记录跨帧合并，一批最多100000行，内容保守估算最多8兆字节。从该分组第一帧进入缓冲开始等待，满1000毫秒、参数行数或整帧数达到行数上限、或者分组字节估算达到上限，任一条件先满足就唤醒后台刷新。后续新帧不会重新计时，避免持续低流量导致永不刷新。

触发刷新表示后台可以取走该组，不代表此刻已经写完。网络慢、队列积压或重试时，等待可能超过1秒。一秒是合并等待配置，不是每秒一个请求或每秒仅允许写一次。

同一组中的参数汇成连续的行序列，整帧也作为行序列批量写入；正常和异常帧保留各自状态。记录不按参数代号压缩成最新值，每帧源时间与处理时间保持不变。超过传输行数或字节上限时按记录边界拆分，单条记录自身超过字节额度会明确失败并进入现有告警链路。分组按整帧接收，取走前可能超过单批额度一个或多个整帧，实际传输仍严格拆批，所有保留记录继续计入全局缓冲额度。

例如每帧10000个参数，只有未先触及8兆字节或1秒条件时才会合并到十帧100000个参数；调大行数上限不会绕过字节上限。功能验证中将字节额度相应提高后，已真实验证十帧十万参数合并写入。

默认4个合并入库工作线程和4个写入通道，每个通道同一时刻只处理一个合并组。同一个对象在前一组写入期间仍能接收新的组，并在不同通道上并行写入。每个“物理表＋通道”独占一个列缓冲和流，参数与整帧使用不同流。

合并缓冲默认共用256兆字节保守估算额度，待合并、正在写入和重试中的记录都占用额度，直到成功或最终失败才释放。超限立即拒绝新记录，由原有接口级入库告警报告；缓冲不会无限增长，不回退到采集线程写数据库。估算不等同于真实堆内存，仍需为对象布局、原有Proto和组装队列保留空间。

流缓存默认保留16项，达到上限后在全局锁外完成并关闭最久未使用的空闲流；不会淘汰正在使用或等待使用的流。单流堆外分配上限默认32兆字节。淘汰和新流创建有短暂重叠，该额度也不是进程总内存上限。

通道额度及表锁的等待上限复用 `greptime.connection-timeout-millis`。每个流只保留一个在途批次，并等待服务端确认再复用缓冲；多个通道提供并发。`data-processing.result.storage-thread-count` 和 `storage-queue-capacity` 现在控制按帧的记录组装及缓冲提交，线程不等待凑满1秒；真正数据库写入并发由 `max-concurrent-writes` 控制。实际吞吐仍受CPU、磁盘和服务端容量影响。

## 配置

管理服务与处理服务的 `greptime.url` 必须连接同一数据库，默认 `sjcl`。处理服务新增以下配置，所有字段均有可用默认值。

```yaml
greptime:
  # 保留原有查询连接、账号、密码、自动建表及有限重试配置。
  bulk:
    # 与查询连接指向同一Greptime集群；本地部署填写本机地址。
    endpoints:
      - 127.0.0.1:4001
    # 跨帧合并后的单批行数上限，同时受字节和等待时间条件控制。
    max-batch-rows: 100000
    # 单批内容保守估算上限，单位为字节。
    max-batch-bytes: 8388608
    # 单个流的堆外分配额度，至少为批次字节额度的两倍。
    allocator-max-bytes: 33554432
    # 按物理表和写入通道缓存的流数量总上限。
    max-cached-streams: 16
    # 同时处理合并组和等待写入确认的工作线程与通道数量。
    max-concurrent-writes: 4
    # 服务端确认及流内部各次等待的超时毫秒数。
    timeout-millis: 30000
    # 从分组第一帧开始等待，满一秒就触发刷新，新帧不会重新计时。
    flush-interval-millis: 1000
    # 待合并、写入中和重试中的记录共用的估算总字节额度。
    max-pending-bytes: 268435456
    # 正常关闭时立即刷新剩余组，最多等待一分钟。
    shutdown-wait-millis: 60000
```

未填写 `endpoints` 时，从 `greptime.url` 推导相同主机的4001端口，不重复配置数据库名或账号密码；需要不同端口或多地址时必须显式填写。仓库Nacos示例使用部署环境的服务域名，本机调试需填写本机地址。原有 `greptime.batch-size` 已移除，其他业务组件的批次配置不受影响。

写入超时范围为1至300秒，批次行数范围为1至100000；批次估算字节上限为128兆字节。并发通道数不能超过流缓存数量。刷新间隔范围为1至60000毫秒，缓冲总额度至少为单批字节额度且不超过16吉字节，关闭等待范围为1至300秒。配置修改后重启处理服务生效，不会自动发布到Nacos。

## 数据语义与失败

字段名、主键和表名沿用现有定义；源时间与处理时间均以毫秒纪元传输，`processed_at` 是普通时间字段，`source_time` 是时间索引。英文类型编码、中文名称、数值、文本、空值及二进制原码都按原字段保存，不依赖SQL字符串转义。

沿用现有非追加表配置，重试保持源时间、处理时间和主键不变。同一主键与同一源时间重复写入仍覆盖已有数据。没有跨参数表与整帧表的原子事务，不能把参数已确认理解成整帧也已确认。

当列缓冲组装、服务端写入、行数确认或等待失败时，关闭当前流；下一次重试会新建流，并从保留的存储记录重新组装，不会复用已经清空的Arrow缓冲。原有 `greptime.write-attempts` 控制包含首次写入在内的尝试次数。重试耗尽由合并入库线程按采集接口记录中文错误与存储告警，成功进入缓冲不能视为已入库。缓冲溢出、进程崩溃和重试耗尽没有新增持久重放保障。

正常关闭时先结束上游记录组装任务，然后停止接受新记录、立即刷新全部剩余分组；所有组完成后再关闭数据库连接和写入流。超过关闭等待上限时中断剩余任务，并明确记录未完成组的错误与告警，不能伪造刷新成功。

原有按包采样的阶段名改为“入库组装排队”和“记录组装和缓冲提交”。合并线程每五秒最多输出一次“遥测跨帧批量入库采样”，包括整帧数量、参数数量、缓冲等待及写入含重试耗时。

“入库组装排队”继续每20帧采样，记录组装及缓冲提交结束后统一打印，排队耗时仍是该任务入队到开始执行的时间。新增“本帧入库估算大小”，包括完整整帧和本帧全部参数，直接复用 `max-pending-bytes` 预算使用的估算结果，不重复遍历参数；该值不是JVM实测内存或网络传输大小。缓冲拒绝时仍打印已获取的估算值；记录尚未组装成功或停用存储时不打印大小，避免用零冒充真实结果。采样上下文在任务结束时清理，组装耗时不包含两条计时日志的输出时间。

```text
PDXP压测计时，接口编号：518，包序号：20，阶段：入库组装排队，耗时：0.038毫秒，本帧入库估算大小：4521984字节（4.31MiB）
```

## 运行环境与发布

使用Java 8编译和运行。传输依赖统一为gRPC 1.78.0、Protobuf 3.25.1、Netty 4.1.127.Final，避免与现有遥测RPC及Redis混用版本；Arrow 14.0.2采用官方 `arrow-memory-unsafe` 分配实现，排除依赖旧Netty内部字段的 `arrow-memory-netty`。需要使用完整构建后的依赖，IDE中重新加载Maven，不能只复制业务class。

部署需要允许处理服务访问Greptime的gRPC端口4001，查询端口仍为4002。先检查配置地址、认证与数据库名，发布完整处理服务构建产物后重启。已有分表可以直接继续写入，结构不匹配时应报错排查，不能通过自动改表掩盖字段类型差异。

验证使用与业务服务分离的临时Greptime 1.2.1实例和独立数据库，覆盖一秒跨帧刷新、行数与字节提前触发、十帧十万参数合并、同对象多接口目录登记、正常与异常帧混合、不同任务及设备卫星隔离、曲线时间点保留、重试固定时间、在途数据额度、最终失败告警和正常关闭刷新；原有单帧、二进制、空值等Bulk验证继续可用。吞吐上限需另做持续压测，功能验证不能作为每秒百万点的容量承诺。
