# 系统健康遥测上报

管理服务从 `system:monitor:current` 读取健康快照，按运行中的试验任务分别组装 `TelemetryMessage`，将 `toByteArray()` 的原始 Protobuf 字节发到 RocketMQ。消息不加自定义头，不经过 PDXP 或 UDP。没有运行任务时不发送，不把消息积压数加入参数表或健康消息；既有页面的积压监控保持原状。

## 配置

配置位于 `nacos-config/data-admin-service.yaml`，同步到 Nacos 后重启管理服务生效。

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `system-monitor.sample-interval-millis` | 1000 | 健康采样及 Redis 更新周期，毫秒 |
| `system-monitor.snapshot-flush-interval-millis` | 30000 | 暂存快照批量入库周期，毫秒 |
| `system-monitor.alarm-duration-millis` | 15000 | 从首次超限采样开始的连续超限等待时间，毫秒 |
| `system-monitor.mq-report.enabled` | true（配置文件） | 是否启用健康消息；未提供配置时默认关闭 |
| `system-monitor.mq-report.interval-millis` | 1000 | 一轮发送完成后到下一轮的等待间隔，毫秒 |
| `system-monitor.mq-report.max-snapshot-age-millis` | 5000 | 快照允许的最大年龄，毫秒 |
| `system-monitor.mq-report.topic` | topic_yc_out_sjcl | 消息目标主题 |
| `system-monitor.mq-report.tag` | 空字符串 | 不指定消息标签 |
| `system-monitor.mq-report.business` | DATA_SUBSYSTEM_CSCL_PHYVALUE | 当前暂用测试测量，枚举值 8 |
| `system-monitor.mq-report.business-id` | sjcl | 参数表业务标识 |

消息调度使用独立线程，每轮串行发送，慢发送不累积额外发送任务。网络发送时间会增加实际两轮之间的间隔。采样、页面推送和数据库持久化沿用业务调度线程；网络或数据库耗时较长时，配置周期不代表严格的实时保证。每轮读取一次快照，向每个任务发送前再次校验快照时效。快照缺失、未来时间、过期或参数不完整时跳过发送。错误日志最多每 30 秒记录一次，下一轮读取最新快照，不补发过期数据。部分任务发送失败不阻断同轮其他任务。

## 消息身份与数据

`proto_head.topic_type` 为 `TEST_DATA_TYPE`；`proto_head.bussiness` 为 `DATA_SUBSYSTEM_CSCL_PHYVALUE`；`proto_head.task_id` 为该运行任务编号；`proto_head.msg_source` 为“数据处理”；`proto_head.msg_time` 为组装时间。`time` 为快照采样时间，按北京时间解释。

`channel_name` 为 `sjcl`，`bussiness_id` 为 `sjcl`，`tm_type` 为 `TM_TYPE_DEVICE_TM`。不填卫星编码、卫星名称、通道编码和分包。全部参数成功编码后将 `frame_check_status` 设为 true。消息本身不写入采集统计和遥测历史表，原有健康快照继续批量入库。

| 序号 | 代号 | 中文名称 | 位宽 | 单位或编码 |
| --- | --- | --- | --- | --- |
| 1 | SJCL001 | 处理服务状态 | 8 | 0停止、1运行中、2查询异常 |
| 2 | SJCL002 | 管理服务运行时长 | 64 | 秒 |
| 3 | SJCL003 | 已启用采集接口数 | 32 | 个；启用不代表网络连接在线 |
| 4 | SJCL004 | 采集接口总数 | 32 | 个；不含已删除接口 |
| 5 | SJCL005 | 数据库连接耗时 | 32 | 毫秒 |
| 6 | SJCL006 | 处理服务心跳状态 | 8 | 0等待心跳、1正常 |
| 7 | SJCL007 | CPU使用率 | 32 | 百分比，原码为物理量乘100 |
| 8 | SJCL008 | 内存使用率 | 32 | 百分比，原码为物理量乘100 |
| 9 | SJCL009 | 磁盘使用率 | 32 | 百分比，原码为物理量乘100 |
| 10 | SJCL010 | 健康评分 | 8 | 0至100，沿用现有评分算法 |

每项参数的 `table_index`、`tm_symbol`、`tm_name` 与 Excel 一致，`system_name` 为“数据处理”。所有参数使用公式类型 301 和 `VALUE_TYPE_DOUBLE`，数值写入 `value`；状态的 `value_text` 使用现有中文枚举标签，其他参数为数值文本。CPU、内存、磁盘保留两位小数，公式为 `x/100`；其他参数公式为 `x`，小数位数为 0。

`raw_data` 是对应无符号整数的固定长度小端字节。`frame_raw_data` 按序号拼接这 10 项原码，共 35 字节，不包含 PDXP 包头或附加帧头。例如 CPU 为 23.45 时，原码整数为 2345，原码字节为 `29 09 00 00`，物理量为 23.45。

当前 Excel 的“是否报警”均填 0，不额外生成参数级 `state_type`、`state_index`、`state_name`，健康告警仍由既有监控规则按配置阈值和持续时间判断。状态码解释保存在“状态跳变信息”列。若任何一项快照数据不可用，本轮不发送整帧，避免以零值代替失败；CPU等资源数据仍沿用现有采样组件的口径。

CPU、内存、磁盘来自管理服务所在机器，运行时长来自管理服务进程；处理服务状态来自注册中心，心跳来自处理服务缓存。因此它们不是同一个进程的全部指标。

## Excel 与接入

`系统健康遥测参数.xlsx` 仅有 `sjcl` 工作表，第一行是现有导入器要求的完整 19 列表头。字段代号、序号、位宽和倍率从 `SystemHealthTelemetryParameter` 枚举提取生成。工作表名按本次约定固定为 `sjcl`，独立健康组装器直接使用该通道名，不要求它具有设备采集链路的“通道名称_业务标识”格式。无需为健康上报创建 UDP 采集接口或本地 PDXP 配置。

消息字段说明同步到 `apifox-openapi.yaml` 的健康遥测消息模型；该模型的 JSON 形式仅供查看字段，不代表新增 HTTP 接口或改成 JSON 消息。
